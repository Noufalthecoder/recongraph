# ReconGraph — Benchmark & Evaluation Harness

> **Authoritative Technical Documentation for Step 8: Benchmark & Evaluation Harness**  
> Package: `backend/app/benchmark/`

---

## 1. Purpose

The ReconGraph Benchmark & Evaluation Harness is an independent evaluation layer designed to measure the detection accuracy and performance of the deterministic reconciliation engine. It compares ground truth anomalies with reconciliation engine findings to objectively compute **Precision**, **Recall**, and **F1 Score**, as well as throughput metrics.

> **Central Benchmark Invariant:**  
> *"The benchmark knows the GroundTruth because its purpose is evaluation. The production reconciliation engine does not."*

---

## 2. Why Benchmark is External to Reconciliation

To guarantee benchmark integrity, avoid label leakage, and ensure production realism:
1. The **Reconciliation Engine** (`backend/app/reconciliation/`) consumes strictly `ObservedWorld` and has **zero access** to `GroundTruth`, `AnomalyManifest`, or synthetic corruption metadata.
2. The **Benchmark Layer** (`backend/app/benchmark/`) runs externally. It takes `GroundTruth`, `AnomalyManifest`, and the `ReconciliationResult` produced by the engine, mapping detected issues to expected anomalies.
3. The benchmark never modifies `ObservedWorld` or influences reconciliation decisions.

## 3. GroundTruth vs ObservedWorld

- **`GroundTruth`** (`simulator/ground_truth/models.py`): The complete, uncorrupted financial record of truth generated by the simulator.
- **`ObservedWorld`** (`simulator/observed/models.py`): The dataset ingested by the reconciliation engine. It is generated by cloning GroundTruth and applying controlled corruptions when anomalies are enabled.
- **`AnomalyManifest`** (`simulator/observed/models.py`): The audit log of injected corruptions (e.g. mutated amount delta, dropped record, duplicate record, modified UTR).

---

## 4. AnomalyManifest Role

The `AnomalyManifest` contains `AnomalyRecord` entries detailing every corruption applied to `ObservedWorld`. The benchmark layer transforms these records into `ExpectedAnomaly` structures to evaluate whether the reconciliation engine deterministically detected each corruption.

---

## 5. Detection Matching Methodology

The `AnomalyMatcher` evaluates detected issues against expected anomalies using a 4-pass deterministic matching hierarchy:

- **Pass 1 — Exact Target Entity:** Direct match on normalized target entity type (e.g., `bank_entry`, `settlement_transaction`, `payment`), target entity ID, and compatible exception type.
- **Pass 2 — Settlement Context:** Matches settlement-level composition shortfalls (`SETTLEMENT_COMPOSITION_MISMATCH`) to expected missing transactions or amount deltas belonging to that settlement.
- **Pass 3 — Referenced Foreign Keys:** Matches `MISSING_RECORD` exceptions on join records (e.g. `SettlementTransaction`) when referencing missing primary records (e.g. omitted `Payment`).
- **Pass 4 — Evidence & Relationships:** Matches unique candidate pairings (e.g., `IDENTIFIER_MISMATCH` with matching candidate UTR / bank entry).

### Ambiguity Rule:
If multiple detected issues compete for a single expected anomaly without unique evidence, the benchmark **never guesses**. Unmatched expected anomalies are classified as False Negatives, and unassigned detected issues are classified as False Positives.

---

## 6. Precision, Recall, and F1 Definitions

All formulas use exact `Decimal` arithmetic rounded using `ROUND_HALF_UP` to 4 decimal places:

$$\text{Precision} = \frac{TP}{TP + FP}$$

$$\text{Recall} = \frac{TP}{TP + FN}$$

$$\text{F1 Score} = \frac{2 \times \text{Precision} \times \text{Recall}}{\text{Precision} + \text{Recall}}$$

### Zero-Case Behavior:
- **Clean Datasets ($Expected = 0$):** If $TP + FP == 0$ and $Expected == 0$, Precision and Recall are defined as $1.0000$ (100%), reflecting zero false alarms on valid data. If $FP > 0$, Precision and Recall drop to $0.0000$.
- **Zero Detections with Expected Anomalies ($Expected > 0, TP = 0$):** Precision, Recall, and F1 are $0.0000$.

---

## 7. False-Positive and False-Negative Definitions

- **True Positive (TP):** An expected anomaly that was successfully detected and matched to an engine exception.
- **False Positive (FP):** A detected exception or unmatched record that did not correspond to any expected anomaly (e.g., spurious exceptions on clean data).
- **False Negative (FN):** An expected anomaly that the reconciliation engine failed to detect.

---

## 8. Clean Dataset vs Anomaly Dataset Evaluation

1. **Clean Dataset Evaluation:**
   - Evaluates all 6 supported synthetic scenarios with zero corruptions.
   - Expected outcome: **100% clean reconciliation rate**, 0 false positives, 0 false negatives, precision = 100%.
2. **Anomaly Dataset Evaluation:**
   - Evaluates scenarios with injected `AMOUNT_MISMATCH`, `MISSING_RECORD`, `DUPLICATE_RECORD`, and `IDENTIFIER_MISMATCH`.
   - Expected outcome: Discrepancies detected with exact mathematical evidence, precision $\ge 90\%$, recall $\ge 90\%$.

---

## 9. High-Volume Batch Benchmark ($\ge 50$ Records)

The benchmark harness includes high-volume synthetic batch generation (`run_large_batch(batch_size)`):
- Synthesizes multi-merchant, multi-order, multi-settlement datasets scaling from 50 to 500+ records.
- Injects multi-type anomalies across the batch.
- Measures throughput ($\text{records/sec}$) and verifies that high-volume reconciliation scales linearly.

---

## 10. Performance Measurement

Performance metrics are measured using standard monotonic timing (`time.perf_counter()`):
- `elapsed_seconds`: Total runtime in seconds.
- `total_records`: Total domain entities evaluated across all scenarios.
- `records_per_second`: Processing throughput.

---

## 11. Determinism Guarantees

1. **Zero Randomness:** Benchmark evaluation uses purely deterministic rules and index comparisons.
2. **Deterministic Output Sorting:** Scenarios, anomaly breakdowns, and evaluation lists are sorted deterministically before reporting.
3. **Idempotency:** Repeated benchmark executions with identical configurations yield 100% byte-identical metric outputs.
